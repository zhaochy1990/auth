# Releases are recorded in a root versions.json; there are no git tags

CalVer `YYYY.M.MICRO` stays, but the version now lives per package in a root `versions.json` instead of the root `package.json`, and nothing is tagged. Release runs in three phases from `release.yml` — `bump-versions` (compute the next version of every package the push touched, writing nothing), `build` (build and push the image tagged with that version), `commit-versions` (record it in `versions.json`, one commit) — via the shared `zhaochy1990/configurations/calver-release` action. `commit-versions` runs last and is handed phase 1's result verbatim: `versions.json` must never name an image that was never published, and recomputing after a mid-build push would name one that does not exist. The old chain (compute CalVer from the newest `v*` tag, `sed` `package.json`, commit, tag, create a GitHub Release, dispatch `deploy.yml` by tag) was shaped for exactly one package and would have produced a tag per package per release.

Status: accepted

Known trade-off: no git tag means no GitHub Release and no ref-based trace — the image tag is the only immutable identity a version has, which is fine here because `stride-devops/versions.env` already pins by image tag. Change detection became path-based rather than commit-type based, so a `docs`/`chore` commit inside `sources/dev/authentication-go/` now cuts a release too (2 of the last 40 commits). And a new package must be seeded in `versions.json` with its currently deployed version, or numbering restarts at `.1` and the deploy PR reads that as a downgrade. The release logic lives in another repository, so a change there reaches this repo without a commit here.
